# Superesearch5.1

Use one coordinator for the interview and plans, five discovery specialists, three analysis workers, three judges, an independent reader and a separate work finisher. After objective approval, proceed through internal review gates to delivery; pause only for the exceptions below. Offer interactive mode at objective approval without adding a separate question.

## Start and resume

Follow repository AGENTS.md, lifecycle and collaboration rules. Use the bundled [research method](references/research-method.md). Host project instructions and recording tools remain environment inputs; no sibling skill is required. For an existing project, read its current brief, refinement, lifecycle and latest answer/review. Resume the user's selected action without repeating completed discovery or approvals. For a new question, give the first checkpoint promptly, before domain research or extensive setup. Keep other projects' evidence out when independence is requested.

This skill controls cadence; do not run another superesearch version as a second workflow. Reuse repository evidence standards and recording tools. If repository recording tools are unavailable, preserve local records and disclose the limitation. This fallback does not replace this skill’s state helper.

Use [role prompts](references/roles.md) when delegating, [review and synthesis](references/review.md) when judging, and [state commands](references/state-cli.md) when recording gates. Keep one authoritative approved brief. Link its version and requirement IDs; do not copy its rules into every plan, prompt or answer. This avoids duplicating process instructions; reader-facing answers must still explain the context and assumptions needed to understand them. Give agents access to the referenced files and require them to read applicable requirements.

Resolve `scripts/research_state.py` relative to this `SKILL.md`, not the project or run directory. Verify that file before claiming it is missing; use its absolute path as shown in [state commands](references/state-cli.md). If it cannot run, report the exact path and error, preserve work and repair the dependency before advancing a gated stage. A handwritten ledger is not equivalent enforcement.

## Cadence

1. **Question.** Show the refined question, intended decision and proposed pillars without web research. Ask at most three consequential clarification questions at a time, with useful suggested answers. **Wait for explicit question confirmation before stating the objective.**
2. **Objective.** State the objective, outputs, definitions, exclusions and completion standard, with stable IDs for every requirement; distinguish user requirements from inferred assumptions. State that approval authorizes autonomous sourcing, planning, execution, repair and reviewed delivery within this brief and any existing limits. The user may choose interactive checkpoints instead. Record the selected mode in the brief. **Wait for explicit approval of this brief and mode.**
3. **Sourcing plan.** The coordinator writes concrete search routes, reuse, priorities and gaps against the approved brief. The independent source reviewer checks that each route addresses an objective requirement, names the evidence sought and gives a concrete next action. Repair vague or untargeted routes; begin discovery only after review passes. No planning competition or routine approval stop.
4. **Discovery.** Assign five searchers: **literature; free datasets; gated datasets; alternative sources; code, tools and technical documentation**. Merge and deduplicate results. An independent source reviewer decides whether coverage is sufficient for execution planning. Repair specific material gaps; stop discovery when it passes. Share a short result update and continue.
5. **Execution planning.** Build the execution plan from the approved objective and sourcing findings: what you will do with each selected source, what it will establish, and how you will combine the findings to answer the question. Make concrete choices; reference rather than repeat the brief and source list. For each planned output, state what the selected sources can establish, what remains assumed or unavailable, and the method or fallback you will use. For decision-critical data, specify **source → data to acquire → operation → question answered**; justify any planned assumption substitution under the acquisition rule below. Give planned tasks and source-use commitments stable IDs linked to the approved requirements. One independent **plan reviewer** records the plan-to-objective table against every approved requirement, checking the brief and sources. Repair material defects; proceed only after it passes. Share the plan clearly as an update, not an approval request.
6. **Execution.** Three workers independently execute the reviewed plan under comparable budgets and shared evidence. Acquire and analyze the data committed in the plan. Trace **acquired evidence → analysis → finding** in existing worker artifacts; record justified exceptions under the acquisition rule below. After a pilot or an inconclusive comparison, the coordinator assesses sufficiency against the objective, not just completion of the sample. Expand coverage or revise the method within scope when feasible next checks could materially improve the answer; obtain affected internal reviews. Before stopping, record the most promising remaining checks and evidence for why they are exhausted, blocked, outside authorization or unlikely to improve the answer materially. Judges verify these commitments against actual evidence and analysis, returning unexplained omissions or assumption substitutions for repair. See [role prompts](references/roles.md) for source-use requirements and [review rules](references/review.md) for targeted repairs.
7. **Synthesis and delivery.** Synthesize the strongest supported findings from all candidates. Reconcile assumptions and calculations, resolve material contradictions, and preserve consequential disagreements. Do not force contributions from every worker or combine incompatible results. Before final judging, run the independent reader test in [review rules](references/review.md) and register it with `reader-test`; partial or missing answers return for repair. All three judges review the actual synthesis and verify every included contribution. Judges complete separate objective and execution completeness tables in the existing review JSON. A separate work finisher verifies both against the brief, plan and final artifacts before delivery; gaps return for targeted repair and re-review. Preserve candidate artifacts.
8. **Extension planning and final response.** Once the work finisher passes, launch an actual **extension planner** subagent against the reviewed final artifact, approved brief and residual evidence gaps, before sending the turn-ending final response. Follow the assignment in [role prompts](references/roles.md); the completed finisher agent may be reused with a new assignment. Wait for its saved `extensions.md` and inspect the result. Present the research answer first, then the planner's ranked follow-on programs and which can run in parallel. A supported finding that no useful extension remains is valid. If delegation is blocked, disclose the specific failure alongside the research answer; do not silently skip the assignment or substitute coordinator-written suggestions. The `deliver` command records research acceptance, not completion of this agent assignment. Do not end the turn with a promise to run it afterward or wait for the user to request suggestions. Required unfinished work returns for repair and affected re-review; optional proposals neither add a research acceptance vote nor authorize launching new programs.

In **interactive mode**, additionally wait for user approval of the sourcing plan, reviewed source list and reviewed execution plan, as in Super4. In either mode, reviewers approve how to answer the question; they cannot redefine it.

Approval binds the displayed stage/version; silence and requested edits are not approval. A message already approving that version counts. Checkpoints and brief process updates are user-facing; failed internal drafts are not, unless requested. Label review updates “Reviewing the sourcing plan” before discovery and “Reviewing the collected sources” after discovery. Keep updates useful and roughly a minute apart during active work.

## Reader-facing memos and answers

Write for an intelligent reader opening the artifact for the first time, with no access to the conversation, brief, earlier memos or internal terminology. Each delivered memo or report must stand on its own, including an exported version.

Start with a plain-language executive summary that briefly states the question and why it matters, the main result or recommendation, and the decisive qualification. Then build the explanation from the beginning: the problem and intended decision; relevant scope, definitions and assumptions; the evidence acquired and work actually performed; findings and reasoning; and implications, limitations and what could change the conclusion. Adapt headings and depth to the task, but do not jump from the summary into analysis whose premises have not been introduced.

Define unfamiliar terms, acronyms, metrics and scenario labels at first use, including in the summary. Explain what consequential assumptions mean, why they were adopted and how they affect the answer; distinguish user constraints, observed facts, analytical choices and unresolved unknowns. Describe the method and evidence sufficiently to explain how the result was reached, without narrating agent orchestration or every research step. Links and appendices provide traceability and optional depth; they must not carry context essential to understanding the main argument. Reintroduce relevant prior findings in follow-up memos rather than assuming the reader remembers them. Keep this proportionate: self-contained does not mean exhaustive or padded.

Preserve analytical specificity when making the answer accessible: retain decision-relevant quantities, units, dates, named entities, source attribution, methodological detail, calculations, scenario distinctions and consequential caveats. Explain technical terms rather than replacing precise claims with generalities. The executive summary is an entry point to the full analysis, not a substitute for it. Add the context needed to understand the detail; do not remove useful detail merely to shorten or simplify the memo.

Apply the first-time-reader check in [review and synthesis](references/review.md) before delivery.

## Brief changes and new evidence

The brief may change when findings or the research flow reveal a necessary revision. First show the proposed change, reason and consequences; **obtain explicit permission before changing the authoritative brief or doing dependent work**. Continue unaffected work. Do not revise scope merely to fit available evidence or improve scores. Preserve the earlier version and permission record; reopen only affected approvals.

Routine evidence additions and method repairs within the approved brief and authorized limits proceed internally. Share evidence with workers and re-review affected plans and claims. Internal plan review may approve method changes only when they preserve the decision, essential assumptions, exclusions and required outputs; it cannot relax these to fit available evidence. Keep proposed brief changes separate from approved records.

Pause dependent work for a necessary brief change, an action needing authorization (such as paid access or outreach), or a material blocker that cannot be resolved within scope or authorized limits. Explain the concrete issue and requested decision; continue unaffected work. Missing data may justify a conditional answer only if the approved completion standard allows it. Never invent permission or turn a blocker into silent scope reduction.

## Proportionate effort and scheduling

Do not impose word targets. Write only what the reader needs to understand the next decision. Discovery locates and qualifies sources; deeper acquisition, extensive parsing and model calibration belong in execution unless specifically included in the sourcing plan. Discovery preview limits do not automatically limit execution; carry promising data routes into acquisition tasks, subject to actual user limits. Do not invent or automatically inherit a discovery time budget. Honor a ceiling explicitly set or approved by the user for this phase; it is not a target. Otherwise stop when the source reviewer finds coverage sufficient for execution planning. Do not repeat budget reminders unless a constraint requires a decision. Prioritize breadth of useful evidence routes before deep inspection of a convenient source.

Use actual subagents, scheduled within available capacity. Five search roles need not run simultaneously: use waves when necessary and report actual concurrency. With four active slots, schedule searchers in waves of three then two, followed by source review; alternate three-worker and three-judge waves later. A persistent worker identity means saved work, not a reserved runtime. Preserve capacity for independent review. Reuse available role identities with saved artifacts where appropriate; a reviewer must not review its own authored work. If delegation fails, try a feasible schedule or resume existing agents. If genuine independence cannot be supplied, disclose the limitation and obtain user agreement to a changed process before substituting it.

Start workers independently with minimal task context; do not share competing drafts before first review. Judges assess independently before seeing other scores. Prefer capable workers; model diversity is not a goal by itself. Follow user/model configuration rather than silently changing models. Keep the review table available to workers; they read current feedback before resubmission.

Follow the targeted-repair and budget rules in [review.md](references/review.md). Repeated repairs without improvement require a changed approach or blocker report, not a lower passing standard. Record elapsed time, available usage, repairs and human interventions separately; do not invent measurements.

## Evidence and records

**Acquire before substituting.** For decision-critical inputs, acquire and use relevant available data within authorized scope. A source listing, documentation or access preview does not complete the acquisition or analysis task. Before substituting assumptions, record a concrete acquisition attempt or an evidence-backed reason acquisition would not help, alternatives considered, and the remaining limitation. One failed preview does not establish unavailability; missing private data does not excuse skipping useful public evidence that can constrain the answer. Respect access permissions and user-set limits, and report consequential blockers. Conditional analysis addresses justified residual gaps only where the approved completion standard permits it.

**Retain deferred paid sources.** In autonomous mode, collect and qualify paid or permissioned source leads through permitted previews even when acquisition is unauthorized. Preserve them in the existing source list/search log with stable IDs and an explicit deferred-access disposition; do not drop them when selecting sources for execution or imply their contents were acquired. Pass those records to the extension planner, which must evaluate them for concrete follow-on inquiries or extensions of the current research using the handoff in [role prompts](references/roles.md). Continue with authorized evidence when the brief permits; an indispensable paid source remains a current blocker requiring a decision, not an optional extension. Preparing a proposal does not authorize payment, subscriptions or outreach.

Keep observations, inference, assumptions and unknowns distinct. Missing private data may permit conditional analysis, not fabricated calibration or empirical probabilities. Check causal links and plausible controls as well as arithmetic. A source's accessibility does not determine its evidential quality. Count shared evidence once.

Only the coordinator updates authoritative project records. Agents write their assigned artifacts. Preserve source IDs, provenance, rejected leads and review reasons; use repository triage, observation, intervention and lifecycle tools. Complete applicable closeout after showing the user the result. Internal approval is not empirical validation.

The state helper records versioned artifacts, dependencies, approvals and review gates. It cannot authenticate user permission, prove agent independence or establish semantic correctness. Stop the work at its gate, not merely its registration. Read its schema rather than inventing command arguments.
